# SPDX image-composition evidence

M7 adds a bounded local proof over the SPDX 3 image SBOM generated by the exact
locked Yocto input. It answers two narrow questions for one selected lab:

1. Were the expected project packages, with their declared licenses, installed
   in the image while the other lab's project packages were absent?
2. Do the selected image files have the same SHA-256 values recorded by the
   generated SPDX graph?

It does not replace the raw SBOM, REUSE, runtime evidence, or release
provenance.

## Run it

Configure the selected lab first, then run:

```bash
./sbom-evidence.sh
./sbom-evidence.sh --lab platform-arm64
```

The no-argument path selects `pci-x86-64`. An explicit empty or unknown lab
fails before source or build access. The wrapper requires exactly one image
target and the exact generator settings documented below.

The default successful output paths are fixed by the selected manifest:

```text
build/evidence/qemu-edu-spdx-image-v1.json
build-platform-arm64/evidence/qemu-edu-spdx-image-v1.json
```

If `BUILD_DIR` relocates the active OpenEmbedded build, the same fixed basename
is written below that resolved build directory. Deployment containment and
effective configuration are checked against the relocated directory; the
project does not silently fall back to the manifest's default path.

Validate a retained document against its own closed semantics:

```bash
python3 scripts/sbom_evidence.py validate \
  build/evidence/qemu-edu-spdx-image-v1.json --require-pass
```

Qualification also binds the document to the current clean revision and
current locked inputs:

```bash
python3 scripts/sbom_evidence.py --repo . --lab pci-x86-64 validate \
  build/evidence/qemu-edu-spdx-image-v1.json \
  --require-pass \
  --require-revision "$(git rev-parse HEAD)" \
  --require-current-inputs
```

`--require-current-inputs` requires every locked source checkout to be ready,
detached, clean, and at its exact commit. A historical document can still be
checked semantically without relabeling it as current.

## Manifest contract

Lab manifest schema 2 adds one closed `supply_chain` object:

- `evidence_profile` is exactly `spdx3-image-v1`;
- `evidence_filename` is the fixed basename above;
- `required_packages` is an ordered list of three project package names and
  their exact declared license expressions;
- `forbidden_packages` is the other lab's three project packages.

The PCI profile expects `kernel-module-qemu-edu` and `qemu-edu-driver` as
`GPL-2.0-only`, plus `qemu-edu-tools` as `MIT`. The ARM64 profile makes the
equivalent assertions for the `qemu-edu-platform` packages. These are project
composition rules, not a claim that the image contains only three packages.

## Collection and validation sequence

The wrapper:

1. enters the exact selected build environment;
2. compares effective DISTRO, MACHINE, and ordered BBLAYERS with the selected
   manifest;
3. reads and verifies all 13 effective SPDX variables with `bitbake-getvar`;
4. verifies the source lock and manifest before task execution;
5. deletes any stale projected evidence;
6. runs `bitbake <image> -c create_image_sbom_spdx`;
7. resolves `DEPLOY_DIR_IMAGE` and `IMAGE_LINK_NAME` from BitBake;
8. reads the stable image SBOM once, with a 128 MiB limit;
9. imports `oe.spdx30` only from the locked OE-Core checkout;
10. validates and projects the graph, writes evidence atomically, then validates
   the generated document against the current clean subject.

A failing task exit is returned unchanged and no evidence is collected. The
projected JSON is limited to 1 MiB, closed to unknown fields, and rejects
duplicate keys, excessive nesting or item counts, control characters, Unicode
surrogates, boolean/integer aliases, path escapes, and symlink artifacts.

## What a passing document proves

Schema version 1 records:

- clean project revision and `0.7.0-dev` identity;
- source-lock digest, exact OE-Core commit, Yocto release, lab-index digest,
  selected-manifest digest, machine, image, and profile;
- exact SPDX 3.0.1 profile and privacy-oriented generator settings;
- one `SpdxDocument`, one build `software_Sbom`, no unresolved internal IDs,
  and the exact rootfs build type;
- one archive-purpose rootfs output and a build-scoped, unique, bounded set of
  install-purpose package inputs;
- all required project packages, their versions and exact declared license
  expressions, and absence of forbidden project packages;
- every root image artifact basename, bounded size, declared SHA-256, and
  independently recomputed SHA-256 from a regular file inside the selected
  deployment directory;
- the successful task exit and eight exact passed checks.

The schema is an external structural oracle. The standard-library semantic
validator additionally enforces dynamic equalities, ordering, count
correlations, current-input binding, and clean-subject qualification that JSON
Schema cannot conveniently express.

## Exact generator profile

The task must resolve SPDX 3.0.1 with profiles `core build software
simpleLicensing security`. Build variables, parent-build identity, timestamps,
kernel configuration, PACKAGECONFIG, sources, compiled sources, and pretty
output are disabled. Supplier names are empty. `SPDX_INCLUDE_VEX=current` is
recorded exactly, but this project does not interpret it as vulnerability-data
freshness.

These settings reduce unstable and potentially private projection inputs; they
do not make the raw SBOM byte-reproducible.

## Deliberate limits

A passing document does not prove:

- full SPDX specification conformance beyond the locked model and project
  graph invariants;
- that all image package licenses have received legal review;
- vulnerability completeness, VEX freshness, exploitability, or absence of
  vulnerabilities;
- bit-for-bit reproducible builds or equivalence between two build hosts;
- a signature, transparency record, attestation, SLSA level, release, or
  physical-hardware behavior.

Raw SBOMs, image files, downloads, shared state, and build trees remain ignored
and are not uploaded by public PR CI. A future signed release/provenance system
needs its own approved threat model, key custody, retention, and verification
design.

## Rollback and compatibility

Reverting M7 must revert manifest schema 2 and its digests together with the
wrapper, collector, evidence schema, tests, CI preflight, project version, and
documentation. Do not downgrade only the manifest number or retain an evidence
profile that older tooling ignores. Historical runtime evidence and diagnostics
documents are separate contracts and remain valid at their recorded revisions.
